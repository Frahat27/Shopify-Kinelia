<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| human → agent conversation | Credentials pasted in a chat turn must reach a secret store and nowhere else |
| agent → shell / git history | A secret passed as a command argument survives in shell history and process listings |
| GitHub repository → the public internet | A public storefront repository exposes offer structure and configuration before launch |
| Shopify GitHub app → repository write access | The integration can commit to the connected branch |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-19 | Information disclosure | Dev Dashboard client secret in transit through the agent | high | mitigate | Secret read from standard input into `gh secret set`, never as a command argument; never echoed; never written to a file; a `secrets-set-manually` path is offered so the developer can bypass the agent entirely |
| T-01-20 | Information disclosure | Public repository | high | mitigate | Repository created private and the private flag asserted by an automated check |
| T-01-21 | Information disclosure | Credential committed to git | high | mitigate | `.gitignore` already covers environment files (plan 01-03); the setup document is negative-checked for token prefixes in both the working tree and its git history |
| T-01-22 | Tampering | Force-push destroying pre-Phase-1 history | medium | mitigate | Explicit prohibition; commit-count and reflog assertions in the acceptance criteria |
| T-01-23 | Elevation of privilege | Shopify GitHub app granted broader scope than needed | low | accept | The integration requires repository write access to commit editor changes back; this is the documented mechanism and there is no narrower scope. Reviewed again at launch |
</threat_model>
