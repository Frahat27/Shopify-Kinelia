<task type="checkpoint:decision" gate="blocking-human">
  <name>Task 1: Lock the base theme (one-way door)</name>
  <decision>Which theme is the base of the Kinelia storefront: Skeleton (build up) or Horizon (strip down)?</decision>
  <context>
    This is the only irreversible decision in Phase 1. Every file in the repository from this
    commit forward inherits it. Undoing it after Phase 2-3 land means re-scaffolding the theme
    and re-authoring every section, block, template and design token on a different component
    model — not a refactor, a rebuild.

    Research (01-RESEARCH.md §1, verified against shopify.dev on 2026-09-07) recommends
    Skeleton and this phase is planned against that default.

    One consequence the developer must ratify along with the choice: the Skeleton starter
    ships ZERO JavaScript — no cart drawer, no predictive search, no pubsub/a11y modules.
    ROADMAP Success Criterion 3 and FOUND-03 were written against a base where those modules
    exist to be preserved ("el cart drawer y predictive search funcionan"). On Skeleton there
    is nothing to strip and nothing to accidentally delete: the risk inverts from over-stripping
    to under-building. Choosing Skeleton therefore also means accepting the FOUND-03 reframe —
    "keep the base minimal + author an ALLOWLIST of what renders", with the cart drawer moving
    to Phase 6 and predictive search to Phase 11. Plan 01-04 records that reframe as an explicit
    deviation for phase verification.

    Dawn is not offered: 2-level section-blocks cannot express the shared multi-avatar block
    library, and it is the legacy OS 2.0 reference.
  </context>
  <options>
    <option id="skeleton">
      <name>Skeleton theme (`Shopify/skeleton-theme`) — build up. RECOMMENDED.</name>
      <pros>Shopify's documented starting point for custom theme development (`shopify theme init` clones it). Same modern theme-block engine as Horizon (8-level nesting, `content_for`) — native fit for the multi-avatar block library. Near-zero JS and one `critical.css`, so the LCP &lt; 2,5 s budget is a question of what we add, not what we failed to remove. Clean fork ownership: the starter changes rarely, so the `upstream` remote is insurance, not a merge treadmill.</pros>
      <cons>No pre-built buy box, cart drawer, variant picker, predictive search, or a11y/pubsub utilities — these become explicit build tasks in Phases 3, 5, 6 and 11 (structure ported from the open-source Horizon components). FOUND-03 / Success Criterion 3 cannot be met verbatim and must be reframed. The third-party `@app` block ecosystem is younger than Dawn's (irrelevant for Etapa 1, which ships no apps in the theme).</cons>
    </option>
    <option id="horizon-stripped">
      <name>Horizon (`Shopify/horizon`) — strip down. Fallback.</name>
      <pros>Ships a working cart drawer, variant picker, predictive search and a11y/pubsub modules on day one. FOUND-03 becomes literally executable as written: strip by not-rendering, keep the cart and accessibility modules. Same theme-block engine, so the multi-avatar architecture is unaffected.</pros>
      <cons>Must audit and disable roughly nine preset sections plus unused blocks, and still carry the web-component runtime weight against a hard mobile perf budget. Inherits upstream churn we will never pull. Heavier theme-editor model. Higher risk of the classic over-stripping failure (deleting a module something else subscribes to).</cons>
    </option>
  </options>
  <resume-signal>Reply `skeleton` or `horizon-stripped`. If `horizon-stripped`, STOP and report back: plans 01-01 through 01-05 assume the Skeleton file inventory and must be replanned before execution continues.</resume-signal>
