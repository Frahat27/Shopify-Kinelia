  <action>
    Write `docs/RELEASE.md` in Spanish. It is the operational contract for how code reaches the
    storefront. Give it these sections:

    `## Topología` — a table with the columns Rama, Tema, ¿Publicado?, Quién lo actualiza. Three
    rows: the main branch maps to the published live theme, updated only by a reviewed merge in a
    low-traffic window; the staging branch maps to an unpublished staging theme with a preview link
    only, updated by every merged pull request and used as the quality-assurance target; and the
    ephemeral local development theme created by the command-line development server, updated by
    whoever is developing. State that this is one store with two themes, not two stores.

    `## Conexión rama ↔ tema (paso irreversible)` — state the verified constraint plainly: the
    GitHub integration binds one branch to one theme permanently, and a connection cannot be
    re-established once disconnected — recovering means creating a new theme. Therefore: connect
    deliberately, connect the staging branch first, and never disconnect to "clean up". Note that
    the integration only connects branches whose theme folders sit at the repository root.

    `## Propiedad del contenido` — resolve the ownership question rather than describing it. The
    rule for this project: the GitHub integration owns the settings data file and the template JSON
    files. A non-developer edits staging in the theme editor, the integration commits those edits
    back to the staging branch automatically, and they reach the live theme through the same pull
    request path as code. Consequences to state: expect automatic commits on the staging branch
    naming the shop and the last editor; rebase before pushing; review those diffs rather than
    reflexively accepting them; and never pull a theme over local work as a way of "syncing". Name
    the alternative that was rejected — git owning the JSON with periodic pulls from the editor —
    and why: higher drift risk with no compensating benefit.

    `## Checklist de release` — a numbered checklist, each item phrased as a check with a pass
    condition, not as a suggestion. Cover: both pull-request checks green, cited by their real job
    names; a staging preview-link walkthrough covering the product page, the cart page, the search
    page and reaching the checkout, with no red console errors and the linter clean; a mobile
    throttled performance run on the reference template meeting the documented budget, pointing at
    the performance budget document rather than restating the numbers; a confirmation that no
    half-built section is referenced by a template the live theme serves; the merge itself, in a
    low-traffic window, followed by watching the integration commit land and the theme update; a
    smoke test of the published storefront; and tagging the release.

    `## Rollback` — what to do when the live theme is bad: revert the merge commit on the main
    branch and let the integration redeploy, and if the storefront must be restored faster than
    that, publish the previous theme version from the store's theme library while the revert lands.
    State that no rollback path involves pushing a theme from a laptop.

    `## Prohibiciones` — the standing rules, each with its reason: never publish to the live theme
    from a developer machine; never push a theme to the published theme from a laptop; never
    disconnect a branch from a theme; never let both git and the theme editor own the same JSON; and
    never put a credential in this repository, not even as an example value.

    `## Autenticación en CI` — a short note that any command-line theme operation in continuous
    integration authenticates with a Theme Access application password supplied through the
    environment variable `SHOPIFY_CLI_THEME_TOKEN`. State that this name is irregular — it does not
    follow the usual flag-to-variable convention — and that using the wrong name does not fail
    loudly, it hangs waiting for an interactive login. Note that this project does not currently run
    any command-line theme deployment in continuous integration, because releases go through the
    GitHub integration; the note exists so that a future workflow does not rediscover this the hard
    way. Note also that workflow runs from first-time contributors require approval, which is the
    intended behaviour and not a misconfiguration.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| staging theme → published live theme | The merge is the only path by which code reaches paid traffic |
| theme editor (non-developer) → repository | Editor writes are automatic commits nobody explicitly authored |
| repository documentation → operator behaviour | An example credential in a runbook becomes a real credential in a terminal |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-15 | Tampering | Direct push to the published theme from a laptop | high | mitigate | Prohibition stated with its reason in the runbook and in the readme's topology summary; releases defined as reviewed merges only; rollback path documented so improvisation is never the fastest option |
| T-01-16 | Repudiation | Automatic theme-editor commits on the staging branch | medium | mitigate | Single named owner for the settings and template JSON; the runbook instructs reviewing those diffs rather than accepting them reflexively |
| T-01-17 | Information disclosure | Credential pasted into a runbook as an example | high | mitigate | Explicit prohibition; the acceptance criteria negative-check the document for Shopify token prefixes |
| T-01-18 | Denial of service | Branch disconnected from its theme, unrecoverable | high | mitigate | The irreversibility is a named section of the runbook, not a footnote; the connection step itself is gated in plan 01-07 |
</threat_model>
