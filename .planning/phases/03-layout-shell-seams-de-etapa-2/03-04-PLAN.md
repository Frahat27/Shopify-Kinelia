<objective>
Finish SHELL-02: a footer that carries Argentina's required legal links without any of them being
broken, a WhatsApp affordance in two places, a newsletter block that ships switched off, and the
written runbook for the parts a person has to do in the admin.

Purpose: the footer is where a sceptical buyer checks whether this store is real — who runs it, what
happens if the product does not fit, how to reach a human. A footer whose legal links point at
not-found pages is worse than a footer with no links, which is why the stub pages exist before the
menu points at them and Phase 11 only has to write the content. The WhatsApp button is the user's
explicit choice over a lighter shell, so this plan builds it and makes it already know how to yield
to the sticky add-to-cart bar Phase 6 will put in the same corner.

Output: the rebuilt footer, the contact glyph, the WhatsApp number setting, the floating button with
its Phase 6 coexistence rule, and the staging runbook.
</objective>

<decisions>
Planner-resolved questions this plan implements. Veto any of these at plan review.

- **Five stub pages, not four.** The four in the phase context, plus the regret-button page, because
  the roadmap's Phase 11 requires that button to be reachable and its footer link may as well point
  somewhere real now rather than being added later as an exception.
- **The slugs are `terminos`, `privacidad`, `cambios-y-devoluciones`, `datos-de-la-empresa` and
  `boton-de-arrepentimiento`.** Unaccented, hyphenated, lowercase — the convention for every other
  identifier in this repository. Research assumption A3 flagged these as the planner's to fix;
  changing one afterwards is a runbook edit, not a code change.
- **The external consumer-defence link is a runbook decision, not code.** Research assumption A4
  could not close the exact Argentine compliance list and flagged it for user confirmation. The
  runbook lists it as an explicit confirm-with-the-developer item rather than this plan quietly
  deciding a compliance question.
- **The floating button lives in the footer section, not in the layout.** The footer group renders on
  every storefront route, so the button is global either way — and inside a section it gets a scoped
  style block, which a layout file cannot have. That keeps its styles under the token checker with
  everything else.
- **The button is a rounded square at the spacing scale's large step, not a circle.** The brand
  system caps corner radius at two pixels and has no elevation; a circular badge with a shadow is the
  house style of exactly the kind of advertisement this brand is trying not to look like.
- **The coexistence rule ships without its trigger.** The style rule that hides the button when the
  page carries the sticky add-to-cart class exists now; Phase 6 adds the class when the bar exists.
  Zero JavaScript for the button in this phase.
</decisions>

    inject markup, which is why the token checker rejects unconstrained setting types there.

    contents belong to the theme editor, not to git, so the code side is only the loop and the
    schema setting. Give the list a heading read from the locale, and wrap the whole container in a
    check on the list's size so an unconfigured menu renders nothing rather than an empty box. Write
    no link target into the template: a target typed here is a target that resolves to a not-found
    page the moment a slug changes, and the runbook in Task 3 is what makes the list real.

    **The WhatsApp affordance.** Add a link whose target is the messaging scheme with the number
    setting interpolated, whose visible label is the existing approved call to action from the brand
    namespace, and which inlines the contact glyph. Open it in a new context and carry the
    no-opener relationship, so the destination cannot reach back into this page. When the number
    setting is empty, render nothing at all rather than a link to a malformed target.

    **The newsletter.** Add the block the starter never had, wrapped in a check on a new section
    checkbox that ships switched off. Inside: the heading and the field labels from the locale keys
    that already exist, and the platform's own customer form. With the switch off nothing renders at
    all — that is the point. Etapa 2's email work turns the switch on; it does not write markup or
    uncomment anything.

    **The payment row.** Keep the starter's block and its checkbox exactly as they are. It is
    conditional on the shop having configured payment methods, so until Phase 12 configures the
    gateway it collapses to nothing on its own — and that is correct, because a footer showing a
    payment icon the store cannot actually accept is the kind of small lie this brand cannot afford.

    **The styles.** Extend the scoped style block: stack the footer's regions vertically on a phone
    and spread them on wider screens, size the contact glyph off the spacing scale, and keep every
    value a token custom property. No literal colour, no shadow, no gradient, no upper-casing outside
    the short-label utility.

    **The editor labels.** Add the schema locale entries for the WhatsApp group, the number setting
    and its note, the newsletter switch and the legal menu heading, in this same change. A schema
    translation key with no value renders as the raw key string in the editor.
